# KrishiAI Shared API — for other KrishiAI projects

Base URL: `https://web.krishiai.live/api`

This is the shared backend every KrishiAI project can call directly:
web app, the Expo mobile app, `cabi.krishiai.live`, `game.krishiai.live`,
and anything else under the `krishiai.live` umbrella. No API key is
required for read endpoints — CORS is open to any `*.krishiai.live`
origin (see `src/lib/cors.ts`), and native app requests (Expo/React
Native `fetch`) aren't subject to CORS at all.

## Versioning policy

- **`/api/v1/*`** — versioned, stable contract. Once shipped, response
  shapes here won't change without bumping to `/api/v2/*`. This is what
  other projects should build against.
- **`/api/*`** (no version prefix) — the original app-internal routes
  (`/api/chat`, `/api/diagnose`, `/api/weather`, etc.). These still work
  and are CORS-open the same way, but their response shapes are not
  contractually frozen — they evolve with the web app's own UI needs.
  Treat them as "works today, may shift" rather than a stable platform API.

New shared/cross-project endpoints should be added under `/api/v1/`.
Existing `/api/*` routes get promoted to `/api/v1/*` opportunistically —
`/api/v1/crops` (below) is the first example of that pattern.

## `/api/v1/crops` — shared crop database

The canonical, durable source of crop category/crop data. Unlike the
legacy `/api/crop-database` (AI-generated into a per-instance in-memory
cache — not persisted, not shared, regenerated by every server restart),
this endpoint persists AI-generated results to Supabase on first request.
Every subsequent call — from any project — reads the same saved rows.

**List categories:**
```
GET /api/v1/crops
```
```json
{
  "ok": true,
  "version": "1.0.0",
  "categories": [
    { "id": "grains", "name": "Grains", "name_bn": "শস্য", "examples": "e.g., Rice, Wheat, Maize", "sort_order": 1 },
    ...
  ]
}
```

**List crops in a category** (generates + persists on first call, served from DB after):
```
GET /api/v1/crops?category=Grains
```
```json
{
  "ok": true,
  "version": "1.0.0",
  "category": "Grains",
  "crops": [
    {
      "id": "...", "category_id": "grains",
      "name": "Rice", "name_bn": "ধান",
      "description": "...", "description_bn": "...",
      "season": "Kharif-2", "source": "ai_generated"
    }
  ],
  "source": "db"
}
```
`source` is `"db"` on cache hits, `"ai_generated"` the first time a
category is requested. Force regeneration with `&refresh=true` (intended
for admin/maintenance use, not routine client calls).

## Other available endpoints (unversioned, stable-in-practice)

| Endpoint | Purpose |
|---|---|
| `GET /api/weather` | Location-based weather + KWI (Krishi Weather Intelligence) |
| `POST /api/chat` | Multimodal AI chat (Gemini → OpenRouter → Groq waterfall) |
| `POST /api/diagnose` | Crop disease diagnosis from photo |
| `GET /api/soil-analysis` | AEZ-zone soil analysis |
| `GET /api/alerts` | Region-based pest/weather/disease alerts |
| `GET /api/crop-prices` / `/api/market` | Live market price data |
| `GET /api/news` | Agri-news bulletin |

All of the above accept the same CORS origins as `/api/v1/*`. See each
route's file in `src/app/api/` for exact request/response shapes until
they're promoted to `/api/v1/`.

## Auth

Everything above is public/anonymous-friendly by design — this is a
farmer-facing utility, not a gated SaaS. `POST` routes tied to a specific
user (chat history, push subscriptions) will attach to the Supabase
session cookie if present, and fall back to anonymous behavior if not.

## For the mobile app (Expo) specifically

The Expo shell app (`krishi-ai-expo`) currently wraps `web.krishiai.live`
in a WebView rather than calling these APIs directly — but any future
native screens can call this same base URL with a plain `fetch()`, no
extra config needed (no CORS restriction applies to native requests).
